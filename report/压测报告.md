# 教育平台 AI 客服服务压测报告

> 执行时间：2026-09-24（Asia/Shanghai）<br>
> 性质：本地 Docker Compose 单机容量验证，不作为生产 SLA 承诺<br>
> 历史实测结论：500 WebSocket、200 msg/s 接入、100 QPS 财务和 20% LLM 超时降级通过；1000 msg/s 突发和当时的单 worker 消费能力未通过。<br>
> 时效性说明：第 2 节主表是优化前基线；第 2.1 节记录了同日对当前版本进行的 2/4 worker 复测。复测发现 PostgreSQL transactional outbox 是新的端到端瓶颈，因此不能只凭 HTTP 吞吐或 NATS consumer pending 判定达标。

## 1. 环境与口径

| 项目 | 实测配置 |
| --- | --- |
| 宿主/容器 | macOS arm64 / Docker Linux Ubuntu 24.04.4 aarch64 |
| Docker 资源 | 2 vCPU / 4,094,455,808 bytes（约 3.81 GiB） |
| Docker | Client 29.8.1 / Server 29.5.2 |
| 工具 | Locust 2.32.6 |
| 服务 | FastAPI + PostgreSQL + Redis + NATS JetStream + Qdrant + worker |
| LLM | 本地 Mock LLM，不消耗真实 DeepSeek 额度 |
| 限流 | 临时调高租户/用户业务限流；LLM 全局调度策略保留 |

题目建议环境为 8C16G，当前经 `docker info` 确认的 Docker 资源只有 2 vCPU / 4,094,455,808 bytes。本报告同时展示需求目标和本机实测上限，但不把所有未达标都归因于硬件。

当前 Compose 虽然启动了 `api`、`api-replica`、`api-replica-2` 三个 API 实例，压测命令的 `--host` 仍固定为 `http://api:8000`，没有通过负载均衡使用其余两个副本；Compose 也只运行一个 worker 容器。所以该轮是“2C4G + 单 API 入口 + 单 worker 容器”基线，不是水平扩展后的架构上限。

## 2. 目标场景结果

| 场景 | 目标 | 实测 | P50 | P95 | P99 | 失败率 | 结论 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| WebSocket 长连接 | 500 | 500/500，保持 60s | 160ms 建连 | 250ms | 260ms | 0% | **通过** |
| 稳定消息接入 | 200 msg/s×5min | 59,675 条，199.12 msg/s | 10ms | 150ms | 220ms | 0% | **接入通过，消费未通过** |
| 突发消息接入 | 1000 msg/s×30s | 10,784 条，370.90 msg/s | 1.2s | 3.9s | 6.2s | 0% | **未通过** |
| 财务查询 | 100 QPS，P95<500ms | 2,908 次，100.08 QPS | 10ms | 130ms | 160ms | 0% | **通过** |
| 20% LLM 超时降级 | 不断链，可用回复 | 129 ACK / 124 完整回复 | ACK 3ms | ACK 9ms | ACK 100ms | 0% | **通过** |
| LLM 超时下首回复 | P95<1.5s | 124 次 | 1.1s | 1.2s | 1.2s | 0% | **通过** |
| LLM 超时下完整回复 | P95<3s | 124 次 | 1.1s | 1.2s | 1.2s | 0% | **通过** |

`199.12 msg/s` 与 200 msg/s 的偏差为 -0.44%，可视为调度误差；但稳定流结束时入站 consumer 仍有 52,836 pending + 1,000 ack pending，因此只能判定接入层达标，不能宣称端到端容量达标。

### 2.1 当前版本多 worker 复测

为避免调用真实模型，本轮把 API 与所有 worker 的 LLM 地址强制覆盖为本地 `mock-llm`，并将业务限流临时调高；数据库连接池按单 API + 多 worker 拓扑收敛为每实例 `pool_size=8`、`max_overflow=4`。压测请求仍只进入一个 API 实例。

| 拓扑 | 时长 | HTTP 请求数 | 实际接入速率 | P50 | P95 | P99 | HTTP 失败 | 端到端结论 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1 API + 2 worker | 5min | 70,317 | 234.69 msg/s | 85ms | 280ms | 440ms | 0 | **接入通过；outbox 积压，端到端未通过** |
| 1 API + 4 worker | 5min | 55,813 | 186.55 msg/s | 180ms | 510ms | 910ms | 0 | **未达到 200 msg/s，且 outbox 积压** |

复测先暴露了两项配置/判定问题：

1. 默认每实例连接池为 `20+20`，多实例总连接数会超过 PostgreSQL `max_connections=100`，曾出现 `TooManyConnectionsError`。表中正式轮次已用 `8+4` 重跑，错误归零。
2. NATS 入站 consumer 在采样中大多接近 `pending=0`，但这并不代表链路追平。停止发压后检查 PostgreSQL，仍有约 6.7 万条 `im.inbound` 与 3.8 万条 `im.outbound` outbox 事件待发布；约 30 秒后分别变成约 6.4 万和 4.0 万。即入站 relay 在排空，但 worker 产生出站事件的速度高于出站 relay，积压从入站转移到了出站。

因此，本轮最重要的结论不是“2 worker 已经达标”，而是：**HTTP 接入能力已经超过 200 msg/s，但 transactional outbox 尚不能持续承载该速率。** 当前 `outbox_relay` 每批只取 20 条，逐条 publish，并且逐条新建数据库会话和提交；这是应先优化和复测的代码热点。4 worker 在 2C4G 上反而让 PostgreSQL 压力更高，不能用增加 worker 数量绕过 relay 瓶颈。

1000 msg/s 突发复测没有在这批积压上继续执行：否则结果会混入前序 backlog，既不能形成有效验收证据，也会给本机数据库继续制造无意义压力。应在 outbox relay 优化、积压安全排空，并为每轮记录 outbox 起止值后重新执行。

### 2.2 DeepSeek 费用边界

- 本轮开始前真实模型历史记录：`deepseek-flash` 11,252 次，788,927 prompt tokens，69,474 completion tokens。
- 本轮检查时真实模型记录仍完全相同；新增 9 条记录的 model 均为 `mock-education`。
- 结论：本轮压测 **没有新增真实 DeepSeek 调用或费用**。供应商控制台仍是最终账单依据。

## 3. 资源与队列

| 场景 | 容器合计 CPU 峰值 | 容器合计内存峰值 | im-inbound pending 峰值 | ack pending 峰值 |
| --- | ---: | ---: | ---: | ---: |
| 500 WebSocket | 28.30% | 1,036.0 MiB | 0 | 0 |
| 200 msg/s | 185.21% | 1,168.76 MiB | 52,836 | 1,000 |
| 1000 msg/s 突发 | 183.89% | 1,160.28 MiB | 约 7.1 万（含前置稳定流） | 1,000 |
| 100 QPS 财务 | 55.28% | 942.8 MiB | 本场景暂停 worker，不计队列 | — |

2 vCPU 在 200/1000 msg/s 历史场景中已接近饱和。当时的有效消费速率约为 25 条/秒，不满足 200 msg/s 端到端目标。当前代码已将 worker 改为 pull batch + 32 有界并发，并让“你好”这类固定问候绕过 LLM；但在 8C16G 固定环境完成同口径复测前，不据此改判为通过。

另外，DeepSeek 全局 `20 starts/s` 是真实 LLM 流量的供应商保护边界，不应与通用消息入口吞吐混为一个指标：

- 本报告 200/1000 msg/s 场景使用固定问候，当前版本不会消耗 LLM 配额，用来验证接入、队列和快速回复链路。
- 若业务要求 200 msg/s 全部都是必须调用 DeepSeek 的复杂问题，则与 20 starts/s 保护上限在数学上不兼容；必须提升供应商配额、增加缓存/固定回复命中率，或接受排队后延迟完成。

## 4. 是否应继续修改代码

### 4.1 判断

**不建议现在为了“做出达标数字”继续盲目修改业务代码，也不应把结论简化为“本机很难跑，所以视为通过”。**

| 影响项 | 当前证据 | 判断 |
| --- | --- | --- |
| 本机资源 | Docker 仅 2C4G，历史压测 CPU 峰值约 184% | 确实是重要上限，不能代表题目建议的 8C16G 环境 |
| API 压测拓扑 | 有三个 API 容器，但 Locust 只请求 `api:8000` | 属于部署/压测拓扑缺口，不是单纯硬件问题 |
| Worker 拓扑 | 已完成 2/4 worker 阶梯实验；4 worker 在 2C4G 上没有优于 2 worker | 本机推荐 2 worker，8C16G 再验证更高实例数 |
| 原始数据时效性 | 已同时保留优化前 baseline 和当前版本复测 | 当前版本接入提升，但端到端仍受 outbox 限制 |
| 核心业务代码 | PostgreSQL outbox 在 NATS 之前形成大规模积压；relay 逐条 publish、逐条 commit | 证据已指向 outbox relay，应先批量化/并发化再复测 |

因此，当前交付结论更新为 **“当前版本在 2C4G、单 API + 2 worker 下可零错误接入 234.69 msg/s，但 PostgreSQL outbox relay 未能同步排空，所以完整端到端指标仍为 PARTIAL；4 worker 受数据库竞争影响反而退化。8C16G 能缓解资源压力，但不能替代 outbox 批量化优化。”**

### 4.2 推荐执行顺序

1. **先优化 outbox relay，不改变业务语义**：一次数据库事务领取一批事件、并发/批量 publish、一次事务批量标记成功；保留 `FOR UPDATE SKIP LOCKED`、失败重试与幂等语义，并增加 outbox pending/oldest-age 指标。
2. **再修压测/部署拓扑**：在 8C16G 独占环境为三个 API 实例增加 Nginx/HAProxy 入口，或使用分布式 Locust 显式分摊流量；worker 从 1/2/4 实例做阶梯实验。连接池总预算必须小于 PostgreSQL `max_connections` 并预留管理连接。
3. **用优化后代码重跑三轮**：每轮开始前确认 outbox 与 NATS 基线，采集入口 QPS、ACK P95/P99、outbox pending/oldest-age、NATS pending/ack pending/排空时间、API/worker/PostgreSQL CPU 和内存、DB 连接池等待。
4. **只对新证据指向的热点继续改代码**：
   - 若 API 仍受 DB 限制，再考虑缓存会话归属、合并去重/归属查询、采用 `INSERT ... ON CONFLICT` 减少往返；
   - 若 worker 受 DB pool 限制，再联动调整 worker 并发与 pool size；
   - 若真实 LLM 队列增长，优先提高短路/缓存命中率或申请供应商配额，不取消 600 在途 + 20 starts/s 保护去换取表面吞吐。
5. **验收口径**：200 msg/s 持续 5 分钟后 60 秒内 outbox 与 NATS 都追平；1000 msg/s 连续 30 秒实际接收约 30,000 条、无丢失，并在报告约定时间内排空。没有完成该复测前，继续标注 `PARTIAL`。
