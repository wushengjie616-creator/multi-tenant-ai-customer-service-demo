# 高并发压测调试全过程

> 执行日期：2026-09-24（Asia/Shanghai）
> 测试对象：当前工作区版本
> 环境性质：macOS Docker Desktop 本地单机验证，不作为生产 SLA
> 最终判定：Outbox 优化后，200 msg/s×5min 已端到端通过；三 API 的 1000 msg/s 目标实测 411.22 msg/s、零失败，仍未达到目标，整体容量为 `PARTIAL`。

> 阅读提示：第 4～9 节保留优化前失败证据与当时判断；第 10 节记录后续代码优化、调参和最终复测，并取代其中的旧“当前结论”。

## 1. 本轮目标

本轮不是单纯追求一个好看的 HTTP QPS，而是回答以下问题：

1. 当前版本采用多 worker 后，是否能稳定接入 200 msg/s？
2. 2 worker 与 4 worker 在本机 2C4G 环境中哪个更合理？
3. 消息是否真正走完 `HTTP → PostgreSQL outbox → NATS → worker → outbound outbox`，而不是只返回了 ACK？
4. 压测是否会调用真实 DeepSeek、产生不可控费用？
5. 未达标究竟是本机资源不足，还是代码/部署配置仍有瓶颈？

第一阶段曾因发现前序 outbox 大规模积压而停止 1000 msg/s 测试；随后已在全新隔离卷完成 Outbox 优化、精确 200 msg/s 和 1000 msg/s 单/三 API 复测，详见第 10 节。

## 3. 压测链路和判定口径

消息链路如下：

```text
Locust
  → POST /webhooks/im/messages
  → PostgreSQL im.inbound outbox
  → API outbox relay
  → NATS im.inbound
  → worker
  → PostgreSQL im.outbound outbox
  → worker outbox relay
  → NATS im.outbound
  → 客户端 / Mock IM
```

因此，以下指标必须分开解释：

- HTTP `202`、P95、失败率：只能证明接入层表现。
- NATS `im-inbound-worker pending`：只能证明已经进入 NATS 的消息是否被 worker 领取。
- PostgreSQL `outbox_events pending/publishing`：用于发现尚未进入 NATS 的积压。
- 完整达标：压测停止后，outbox 与 NATS 都应在约定时间内追平，且消息无丢失。

本轮最初只持续观察了 NATS consumer，后来增加 PostgreSQL outbox 检查。这一补充改变了结论：NATS 入站 pending 接近 0 并不代表端到端追平，因为事件可能还滞留在 NATS 之前的数据库 outbox。

### 4.7 关键复核：NATS 看似追平，但 outbox 没有追平

两轮正式压测中，NATS `im-inbound-worker` 的 pending 通常接近 0，最初看起来像是 worker 已追平。停止发压后增加 PostgreSQL outbox 查询，得到以下连续采样：

| 采样 | `im.inbound pending` | `im.outbound pending` | 解释 |
| --- | ---: | ---: | --- |
| T0 | 67,021 | 37,991 | 大量消息仍在数据库 outbox |
| 约 30 秒后 | 63,985 | 40,143 | 入站减少，但出站增长 |
| 后续采样 | 58,345 | 44,463 | 积压继续从入站转移到出站 |

这说明：

1. API 已经把大量请求接收并写入数据库，所以 HTTP 指标很好。
2. 入站 relay 正在把事件搬到 NATS，worker 也能快速领取。
3. worker 生成的出站事件速度超过出站 relay 的发布速度。
4. 仅看 NATS pending 会遗漏 NATS 之前的数据库积压。

当前代码证据位于 `app/services/outbox_relay.py`：

- `BATCH_SIZE = 20`。
- 每批事件按顺序逐条 `publish_bytes`。
- 每发布一条，再新开数据库 session、读取该行并单独 commit。
- 循环末尾固定 sleep 0.1 秒。

所以瓶颈不只是 2C4G。更大的机器能够缓解 CPU/IO 压力，但逐条发布和逐条提交仍是结构性热点。

### 4.8 为什么没有继续跑 1000 msg/s

发现 outbox 积压时，前序测试已经改变了下一轮的初始状态，而且本轮没有在发压前记录干净的 outbox 起始值。若继续运行 1000 msg/s：

- 无法区分新增积压和历史积压。
- 无法准确计算该轮排空时间。
- 会继续扩大数据库与磁盘压力。
- 可能让“入口接受成功”误报为“端到端成功”。

因此停止突发测试是为了保证证据有效性，不是回避失败。历史 1000 msg/s 结果仍保留在 `report/raw/burst1000_*`，当前版本必须在 outbox 优化和干净基线下重新测试。

## 5. 第一阶段结论（已被第 10 节最终复测取代）

| 问题 | 结论 |
| --- | --- |
| 本机能否接入 200 msg/s？ | 能。2 worker 正式轮达到 234.69 msg/s，0 HTTP 失败，P95 280ms。 |
| 是否已完成 200 msg/s 端到端验收？ | 否。PostgreSQL outbox 大量积压，不能判为完整通过。 |
| 4 worker 是否优于 2 worker？ | 在当前 2C4G 环境不是；吞吐更低、延迟更高。 |
| 未达标是否只因本机不是 8C16G？ | 不是。硬件是限制之一，但 outbox relay 有明确代码瓶颈。 |
| 本轮是否消耗 DeepSeek？ | 没有；真实模型使用记录未增加。 |
| 1000 msg/s 当前版本是否复测？ | 没有；为避免污染证据，在发现 outbox 积压后主动停止。 |

面向面试官的准确表述应为：

> 当前版本在 2C4G Docker 环境、单 API + 2 worker 下实现了 234.69 msg/s 的零错误接入，ACK P95 为 280ms；但端到端复核发现 PostgreSQL transactional outbox 无法同步排空，因此完整高并发验收仍标记为 PARTIAL。定位到 relay 的逐条发布、逐条事务提交是主要热点，下一步应先做批量化，再在 8C16G 多实例环境复测。

## 6. 下一轮优化与复测方案

### 6.1 代码优化

1. 一次事务用 `FOR UPDATE SKIP LOCKED` 领取一批事件。
2. 对该批事件进行有界并发发布，不能无限 `gather`。
3. 发布成功项在一次事务内批量更新为 `published`。
4. 失败项保留单项错误、重试次数、退避时间和幂等 message id。
5. 增加 outbox `pending_count`、`publishing_count`、`oldest_pending_age` 指标。
6. 为批量成功、部分失败、崩溃后 stale claim 回收补行为测试。

### 6.2 测试前置条件

每轮必须记录：

- outbox 各 subject/status 起始值。
- NATS 各 consumer pending/ack pending 起始值。
- 数据库连接数与连接池预算。
- `llm_usage` 按 model 的起始值。
- 当前 Git commit、Docker CPU/内存和容器拓扑。

测试租户应使用独立 ID。测试结束后只能按该测试租户范围清理，不能全表删除或清空真实演示租户数据。

### 6.3 正式验收顺序

1. 2 worker，200 msg/s × 5 分钟。
2. 4 worker，200 msg/s × 5 分钟，用于判断 8C16G 下扩展效率。
3. 1000 msg/s × 30 秒突发。
4. 每轮停止发压后继续观察，直到 outbox 和 NATS 都追平或达到失败超时。
5. 报告 HTTP ACK、完整回复、最大积压、oldest age 和排空时间，不能只报告入口 QPS。

建议验收标准：

- 200 msg/s 持续流：HTTP 失败率 < 0.1%，ACK P95 < 300ms，停止后 60 秒内端到端追平。
- 1000 msg/s 突发：30 秒实际接收约 30,000 条，无丢失，并在报告约定时间内排空。

## 10. Outbox 优化后的迭代与最终复测

### 10.1 TDD：先复现单轮只能处理 20 条

新增 `test_outbox_relay_publishes_large_batch_concurrently`，一次创建 25 条 Outbox 事件。旧实现单轮只返回 20，测试稳定失败：

```text
assert 20 == 25
```

实现批量领取、有界并发发布和批量状态更新后，该测试与终态失败测试均通过；完整 `test_p2_reliability.py` 5/5 通过。失败重试、最大尝试次数、`FOR UPDATE SKIP LOCKED` 和 NATS message id 语义均被保留。

### 10.2 指标采集补全

`scripts/capture_load_metrics.py` 原本只记录 Docker 与 NATS，无法直接证明 PostgreSQL Outbox 状态。新增 Prometheus 解析测试，先得到空结果断言失败，再实现并只采集：

- `eduai_outbox_events`
- `eduai_queue_pending`
- `eduai_queue_ack_pending`
- `eduai_dead_letters_open`

后续每一轮原始 JSONL 都能同时复核容器资源、Outbox 和 NATS。

#### 10.2.1 一次无效 smoke 轮次

首次 smoke 命令没有把宿主机的 `LOADTEST_SCENARIO=stable` 显式传入容器，Locust 实际加载了默认 `MixedCustomerUser`，同时产生 Webhook、财务、知识查询和 WebSocket 请求。该轮零失败，只能证明链路可用，不能作为容量证据。原始文件 `outbox-optimized-smoke_*` 被保留用于说明为什么后续命令全部使用显式 `-e LOADTEST_SCENARIO=...`。

### 10.3 第一组参数：batch=200 / concurrency=50

在全新 `eduai-perf2` Compose project、全新 PostgreSQL/Qdrant 卷、1 API + 2 worker 上执行 50×5、5 分钟：

| 指标 | 结果 |
| --- | ---: |
| 请求数 | 60,980 |
| 吞吐 | 203.69 msg/s |

端到端不再形成历史级积压，但 relay 并发过高会和 API 争用 PostgreSQL，使 ACK P95 超过 300ms。因此没有把“排空快”误判为整体达标。

### 10.4 参数收敛：batch=100 / concurrency=20

60 秒短测达到 244.30 msg/s、0 失败、P95 230ms。随后 50×5 的 5 分钟高于目标负载复测得到 70,131 条、234.53 msg/s、0 失败、P95 290ms。停止时约 1.3 万条瞬态积压在 37 秒内降至 41，约 82 秒观测到精确零。

该轮 ACK 达标，但由于负载高于 Word 的 200 msg/s，且精确零超过自定 60 秒门槛，仍未把它写成正式通过。

### 10.5 1000 msg/s：单 API 失败基线

500 users×10 req/s、30 秒：6,962 条、239.14 msg/s、6 次失败、P95 4.1s。API 日志给出直接根因：

```text
sqlalchemy.exc.TimeoutError: QueuePool limit of size 8 overflow 4 reached
```

Outbox 与 NATS 最终排空，说明当轮首先卡在 API 数据库连接池，而不是 relay。

### 10.6 三 API 客户端分流

先以测试固定虚拟用户到 API endpoint 的 round-robin 分配，再实现 `LOADTEST_API_HOSTS`。启用 3 API + 2 worker，并把总连接预算控制为 84（小于 PostgreSQL 100）：

| 指标 | 单 API | 三 API |
| --- | ---: | ---: |
| 请求数 | 6,962 | 11,980 |
| 吞吐 | 239.14 msg/s | 411.22 msg/s |
| 失败 | 6 | 0 |
| P95 | 4.1s | 2.4s |
| 停压后 Outbox 归零 | 已归零 | T+20s |

水平扩展使吞吐提高约 72%并消除连接池错误，但仍只达到 1000 msg/s 目标的约 41%。因此扩容路径被证明有效，目标本身仍严格判为失败。

### 10.7 最终精确 200 msg/s 正式轮

为避免用 234 msg/s 的高于目标负载代替题目口径，另建 `eduai-finalperf` 全新卷，使用 40 users×5 req/s、1 API + 2 worker，完整执行 5 分钟：

| 指标 | 结果 |
| --- | ---: |
| 请求数 | 59,129 |
| 实际吞吐 | 197.755 msg/s |
| 失败 | 0 |
| 平均延迟 | 69.17ms |
| P50 / P95 / P99 / Max | 50 / 200 / 270 / 620ms |
| Outbox pending / publishing 峰值 | 149 / 128 |
| NATS pending / ack pending 峰值 | 86 / 161 |
| 停压后 Outbox | T+0s、2s、5s、10s、20s、30s、45s、60s 全为 0 |
| 停压后 NATS | pending=0、ack pending=0 |

该轮满足持续时间、吞吐调度容差、P95、零错误和端到端排空要求，正式判定 **PASS**。

### 10.9 当前准确结论

| 问题 | 最终答案 |
| --- | --- |
| 200 msg/s 是否端到端通过？ | **是**。197.76 msg/s×5min，P95 200ms，0 失败，停压即排空。 |
| Outbox 结构性瓶颈是否修复？ | **是**。批量领取、并发发布、批量确认已实现并有回归测试。 |
| 1000 msg/s 是否通过？ | **否**。三 API 在 2C4G 达到 411.22 msg/s、0 失败。 |
| 多 API 是否有效？ | **有效**。相对单 API 吞吐约提升 72%，连接池错误归零。 |
| 是否消耗真实 DeepSeek？ | **否**。隔离库没有新增 LLM usage，真实调用和费用新增为 0。 |

面向面试官的最终表述：

> 在本机 2C4G 环境中，优化后的系统已通过 200 msg/s 持续 5 分钟的完整端到端验收，ACK P95 200ms、零错误、停止时 Outbox 与 NATS 均已追平。1000 msg/s 突发经三 API 水平扩展后从 239.14 提升到 411.22 msg/s并消除错误，但受本机资源和单 PostgreSQL 拓扑限制仍未达标；该项保持失败，建议在题目指定的独占 8C16G + ingress/PgBouncer 环境继续验证。
