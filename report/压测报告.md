# 教育平台 AI 客服服务压测报告

> 执行时间：2026-09-24（Asia/Shanghai）
>
> 环境：macOS Docker Desktop，2 vCPU / 约 3.81 GiB RAM
>
> 性质：本地单机容量验证，不作为生产 SLA
>
> 安全边界：全部容量测试强制使用本地 Mock LLM，真实 DeepSeek 新增调用与费用均为 0

## 1. 最终结论

- **200 msg/s 稳定流通过**：精确口径实测 197.76 msg/s、持续 5 分钟、59,129 条、0 失败，ACK P95 200ms；停止发压时 PostgreSQL Outbox 已为 0，60 秒复核仍为 0，NATS pending/ack pending 均为 0。
- **1000 msg/s 突发未通过**：单 API 因数据库连接池耗尽仅达到 239.14 msg/s并出现 6 次失败；改为 3 API 客户端分流后达到 411.22 msg/s、0 失败，吞吐提高约 72%，但仍未达到题目目标。
- **500 WebSocket、100 QPS 财务、20% LLM 超时降级通过**：沿用同日已保存的正式原始证据。
- Outbox relay 的逐条发布/逐条提交瓶颈已经修复；当前 1000 msg/s 的主要边界转为 2C4G 本机资源、单 PostgreSQL以及缺少真正的外部负载均衡入口。

| 项目 | 配置 |

## 5. Outbox 优化和调参证据

优化前 relay 每批 20 条、串行发布、逐条新建会话并提交，稳定流会在 PostgreSQL Outbox 中形成持续积压。实现改为：

1. 一次事务使用 `FOR UPDATE SKIP LOCKED` 领取一批事件；
2. 使用有界 `asyncio.Semaphore` 并发发布；
3. 成功项在一次事务中批量标记；
4. 失败项仍逐项保存错误、退避、重试次数和幂等 message id；
5. 参数通过环境变量配置，并增加应用 Outbox/NATS 指标采集。

调参过程：

| 轮次 | relay 参数 | 负载 | 吞吐 | P95 | 结果 |
| --- | --- | --- | ---: | ---: | --- |
| 初始并发版 | 200/50/20ms | 50×5，5min | 203.69 msg/s | 420ms | 链路排空快，但数据库竞争使 ACK 超标 |
| 收敛短测 | 100/20/20ms | 50×5，60s | 244.30 msg/s | 230ms | 0 失败，确认方向正确 |
| 高于目标复测 | 100/20/20ms | 50×5，5min | 234.53 msg/s | 290ms | 0 失败；约 82s 出现精确零，超出 60s 严格口径 |
| 最终精确口径 | 100/20/20ms | 40×5，5min | 197.76 msg/s | 200ms | 0 失败，停压即排空，**通过** |

这说明调优不能只追求 relay 并发度：过高并发会与 API 竞争 PostgreSQL；100/20 是当前 2C4G 环境的更平衡点。

## 6. 1000 msg/s 突发迭代

### 6.1 单 API 基线

500 users × 10 req/s，持续 30 秒：6,962 条、239.14 msg/s、6 次失败，P95 4.1s。日志明确出现 SQLAlchemy `QueuePool` 超时，说明入口数据库连接池是当轮失败原因，而不是 NATS 或 Outbox 丢消息。

### 6.2 三 API 分流

Locust 增加 `LOADTEST_API_HOSTS`，虚拟用户按序分摊到三个 API 副本；连接总预算控制在 PostgreSQL 100 连接以内。

| 指标 | 结果 |
| --- | ---: |
| 请求数 | 11,980 |
| 实际速率 | 411.216 msg/s |
| 失败数 | 0 |
| 平均延迟 | 1.173s |
| P50 / P95 / P99 | 1.1s / 2.4s / 3.3s |
| 最大延迟 | 6.0s |
| 停压后 Outbox | T+20s 为 0 |
| 停压后 NATS | pending=0，ack pending=0 |

相对单 API，吞吐提高约 72%，连接池错误归零，证明水平扩展路径有效；但实测仅为目标的约 41%，因此仍判定 **FAIL**。三 API 本机测试中 PostgreSQL 峰值约 75.98%，两个 worker 各约 58%～59%，同时 Docker 只有 2 vCPU，继续堆容器会增加调度竞争。

原始证据：`report/raw/outbox-optimized-burst1000_*`、`report/raw/outbox-optimized-burst1000-3api_*`。

## 7. DeepSeek 成本核验

- 所有容量容器显式覆盖 `DEEPSEEK_API_URL=http://mock-llm:8101/v1/chat/completions`、测试 key 和 `mock-education` model。
- 最终稳定流与突发流使用“你好”快速路径；隔离数据库的 `llm_usage` 没有新增记录。
- 因此本轮真实 DeepSeek 调用数、token 与费用新增均为 **0**。供应商控制台仍是最终账单依据。

## 8. 生产扩容建议

1. 在题目建议的独占 8C16G 环境，用 Nginx/Ingress 统一承接三个以上 API 副本，而不是让压测端自行分流。
2. PostgreSQL 使用 PgBouncer，并按 `实例数 × (pool_size + overflow)` 做总预算；本项目默认已从 20+20 收敛为 8+4。
3. 将 API 写入库、Outbox relay、worker 消费和 Mock IM 分别采集速率及 oldest-age，避免只看入口 QPS。
4. 1000 msg/s 目标需在 8C16G 上重新执行 30 秒并记录约 30,000 条实际接收、无丢失和排空时间；在取得该证据前保持 FAIL。
5. 真实复杂问答还受全局 20 次/秒 LLM 启动保护限制；高入口吞吐依赖固定回复、缓存和 RAG 短路，不能把 1000 msg/s 理解成 1000 次/秒 DeepSeek 调用。
