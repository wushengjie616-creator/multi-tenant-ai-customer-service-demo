# AI 客服意图识别与 RAG 检索优化报告

> 日期：2026-09-26（Asia/Shanghai）
> 范围：AI 客服的「意图分类 + 知识检索（RAG）回复」链路
> 目标：把意图判定从「死板的硬匹配」升级为「规则优先 + LLM 兜底」的两级架构，并在不破坏任何固有功能的前提下，让检索与回复更准、更可控。

## 1. 一句话结论

**意图识别从"18 类硬编码规则死板判定"升级为"规则优先命中粗粒度一级意图、规则打不中时由 LLM 补判二级具体意图"的两级架构；RAG 检索与答案合成带上了意图上下文；命中词库按真实语料扩充到 12 类场景。全量回归与 100 句真实语料对照全绿，其余固有功能零感知。**

## 2. 优化前的问题

优化前的意图识别是一套**扁平的关键词硬匹配**：命中哪个词就落进哪个意图，意图粒度又粗又散，且存在三个真实痛点：

| 痛点 | 表现 | 后果 |
| --- | --- | --- |
| 意图枚举过散 | 意图拆成 18 类，边界靠关键词堆砌 | 同一类用户诉求被拆进多个意图，后续路由分支跟着膨胀 |
| 未命中即「无解」 | 规则打不中时直接落到兜底/无依据 | 覆盖不到的口语化表达被一刀切，体验差 |
| 检索不感知意图 | RAG 只拿用户原话做向量检索 | 意图信息在检索和合成环节被丢弃，召回与回复偏题 |

## 3. 优化方案

### 3.1 两级意图架构（规则优先 → LLM 兜底）

核心思路：**规则负责"快而稳"的粗粒度分流，LLM 负责"慢而准"的细粒度补位**。

```
用户消息
   │
   ▼
规则判定 classify_intent ──命中──▶ 一级意图（粗粒度，直接走对应分支，不生成二级意图）
   │
   ▼ 打不中（unknown）
LLM 兜底 classify_intent_with_llm
   │
   ▼ 输出
一级意图（仍限定白名单） + 二级意图（LLM 概括的具体意图）
```

- **一级意图只做粗粒度大范围**：约束在一个固定的 7 类白名单内（白名单是架构约定，此处不展开），用于路由到"知识 / 财务 / 提醒 / 转人工 / 平台指令 / 闲聊"等大方向。
- **二级意图是 LLM 概括的具体意图**：仅当规则打不中、走 LLM 兜底时才会生成（如"英语课的进度"→ 二级意图"查询英语课学习进度"），用于给后续检索补上下文。
- **规则命中时一律不生成二级意图**：规则命中的场景是确定性的，不额外烧一次 LLM，省时省配额。

> **为什么当前「意图识别」先走硬编码而非 LLM 直接判定**：现阶段不确定生产环境高并发下 LLM 调用是否会排队积压（共享配额 / 超时风险），故先用确定性规则扛住主流量；若后续确认 LLM 容量充足，可把这一步改为 LLM 直接判定，语义理解效果会更好——该开关在 `app/services/assistant_service.py` 的 `generate_reply` 中单点调整即可（真实生产环境可按需切换）。

### 3.2 命中词库扩充（L0–L8 分层优先级）

把原来扁平的词表改成**按语义优先级分层的命中词库**，用"先消歧、再分流"的顺序解决多义词打架：

| 层 | 职责 | 例子（解决的问题） |
| --- | --- | --- |
| L0 | 转人工歧义消解 | 「人工智能/人工成本」不误判为转人工；「真人客服」才转人工 |
| L1 | 请假/考勤/补课**规则类** → 知识 | 「请假规则」走知识，不走「提交请假」指令 |
| L2 | 政策/FAQ/服务协议 → 知识 | 「退费政策」走知识，不走「退费进度」财务 |
| L3 | 财务（进度/到账/支付/消费） | 「我总共消费了多少钱」走财务 |
| L4 | 提醒/日程/闹钟 → 提醒 | 「上课提醒」走提醒，不落入课程知识 |
| L4.5 | 续费「政策/优惠」类 → 知识 | 「老学员续费有折扣吗」走知识，不误判为停续费指令 |
| L5 | 平台指令（含自动续费高风险） | 「怎么关闭自动续费」是高风险指令，带二次确认 |
| L6 | 知识域（招生/师资/价格/教材/账号/课程） | 口语化问法「多少钱/在哪里/几点上课」都能落到知识 |
| L7 | 闲聊（问候 + 身份识别） | 「你是真人还是机器人」判闲聊，不判转人工 |
| L8 | 无命中 → LLM 兜底 | 规则没把握的交给 LLM，不硬猜 |

分层顺序保证了「政策 vs 进度」「指令 vs 规则」「身份 vs 转接」这些历史容易打架的边界被显式钉死。

### 3.3 RAG 带意图检索与合成

RAG 不再只拿用户原话，而是**用户原始消息 + 一级/二级意图**一起参与：

- 向量检索与词面精排的 `search_question` = 原话 + 意图上下文拼接；
- 证据命中后交给 LLM 合成时，提示词里先声明「用户意图」，让 LLM 在可信证据范围内贴着意图作答。

这样意图信息贯穿"检索 → 合成"全程，而不是在意图判定后就丢掉了。

### 3.4 课程咨询「技能」：LLM 语义抽取 + 确定性推荐引擎

课程咨询（选班/选课）也统一到「规则优先 + LLM 兜底」的同一套哲学，并把这项能力包装成一个**给 LLM 的「技能」（skill）契约**（`app/services/course_consult_service.py` 的 `COURSE_CONSULT_SKILL`）：

- **LLM 只负责语义与话术**：把家长口语化表达（如「我家孩子刚上小学、想学点奥数」）抽取成槽位，并把确定性候选渲染成自然推荐话术；
- **确定性引擎负责事实**：班型推荐仍由 `course_recommendation` 按「年级硬过滤 + 兴趣/基础/目标打分」算出，LLM 不参与班型决策，从根上杜绝编造班型/价格/校区；
- **技能契约约束输出**：LLM 只返回结构化 JSON（槽位枚举 + 推荐话术），应用侧对每个槽位做白名单枚举校验，非法值一律拒绝——相当于 skill 的「输入/输出 schema」；
- **确定性兜底**：规则抽取 + 确定性模板始终保留，LLM 失败 / 输出非法 / 演示租户的 mock LLM 都会自然回退，不引入任何编造风险。

这样课程咨询与知识、闲聊、转人工等分支一样吃到 LLM 的语义红利，但「班型事实」始终由确定性代码兜底——正是「LLM 只做受限的语义与话术，不做事实执行器」这一原则在技能层的落地。

## 4. 安全与可控（为什么不会越界）

- **LLM 只做"受限分类器"，不做"工具执行器"**：兜底 LLM 输出的一级意图必须落在白名单内，平台指令类动作仍走既有的 action 允许清单；涉及付费/续费/删除时强制返回 unknown，绝不擅自执行。
- **意图白名单 + 平台动作清单双重约束**，置信度低于阈值（0.6）直接回落安全兜底，不冒险路由。
- **多租户隔离、脱敏、审计、二次确认等固有安全门不变**：越权/注入类语句仍靠"租户隔离 + 高风险二次确认"兜住，意图分类本身不负责安全，也绝不放宽安全。

## 5. 回归安全（对其他固有功能零感知）

本次只动"意图分类 + RAG 回复"这条链路，改动前先锁死三处共享面 + 两处间接共享点，并把回归检查固化成一个可复用的 skill（`.claude/skills/ai-customer-service-regression-check/SKILL.md`）：

- **冻结契约**：意图枚举、`answer_question` 签名、`deterministic_embedding` 算法、`classify_intent` 高优先级规则顺序等关键契约，改动前后逐一核对；
- **分区回归**：财务/提醒/人工转接/平台指令/流式/知识库管理/多租户隔离/安全等 12 个固有功能分区各自跑对应测试；
- **全量门禁**：`make test`（单元 + 集成 + 覆盖率 70% + E2E）+ `make evaluate`（50 条固定路由 + 5 条 RAG 金标）。

以后每一次对 AI 客服算法的改动，都按这份 skill 跑一遍，确保"优化只发生在知识分支内部，其他板块零感知"。

## 7. 边界与说明

- **未命中规则不等于失败**：两级架构里"规则打不中 → LLM 兜底补二级意图"是设计内路径，4 条兜底样本（如"我这个月都有哪些课""怎么修改手机号"）由 LLM 补判，最终同样能正确路由到知识分支。
- **白名单是架构约定**：一级意图始终限定在固定 7 类白名单内，保证下游路由分支稳定、可枚举、可回归；白名单内容在代码 `app/services/intent_service.py` 的 `INTENT_WHITELIST` 中单点维护，本报告不展开。
- **不改变固有功能边界**：财务/提醒/转人工/平台指令/闲聊五个非知识分支的行为与既有契约完全一致，本轮优化只在"意图分类 + 知识检索"内部生效。

## 8. 后续演进方向（预留，本 demo 未实现）

> 本节是"生产可做、demo 不做"的预留思路：当前 demo 用**确定性方案**已经能稳定演示（零外部依赖、零下载、结果可复现），下面的向量相似度增强留作后续演进，不进入本轮实现。

**现状（确定性对齐 + 确定性检索）**

- 知识图谱的**节点/边对齐**靠"归一化名字精确相等 + uuid5 稳定 hash"（`graph_extraction.py` 的 `stable_node_id`/`stable_edge_id`）：同一实体只有名字归一化后逐字一致才会落到同一节点/边，是 identity 对齐，不涉及语义。
- RAG 检索的三重召回里，向量层用的是 `deterministic_embedding`（`rag_service.py`）：64 维字符 hash 向量，纯 Python（hashlib + math）实现，**零依赖、零下载、结果确定**；再叠加实体召回、文本召回，最后用 2-gram 字面重叠算精度，低置信度才交给 LLM 重排。

**可做的增强（后续方向）**

| 增强点 | 现状 | 可升级为 | 收益 / 代价 |
| --- | --- | --- | --- |
| 节点/边实体对齐 | 名字精确相等 | 语义向量相似度召回（先 blocking 出候选 → 算相似度 → 过阈值进 `aliases`，**不硬合并**） | 覆盖"同一老师/班型不同写法"；代价是引入向量模型 |
| 重名消歧 | 无 | 入库规范加约束：教师**全名** + 出生年月等匹配信息 | 从数据侧降低重名撞 hash 风险，仍是确定性手段 |
| RAG 低置信度兜底 | 0 二字符重叠 → 别名/同义扩展 → LLM 重排 | 阶梯中段再加一层**语义向量相似度**兜底 | 减少 LLM 重排次数、提升低置信度命中率 |

**成本说明（为何 demo 不做）**

- 当前 `deterministic_embedding` 是**零成本**方案：不下载任何库，一行 `import` 都不用加。
- 换成真正的语义向量有三档成本：① 本地模型（需下载 embedding 库 + 模型权重，占用磁盘/内存）；② 自建向量服务（部署 + 运维）；③ 调用 embedding API（按 token 计费）。无论哪档，都是**纯新增成本**，对"演示 RAG 有心意、完整"这个目标不是必须项。

**结论**：语义 embedding 对生产环境的**召回上限与消歧能力**有真实提升，值得在后续迭代中评估；但本轮 demo 刻意保持在"确定性、可复现、零新增依赖"的闭环内，向量相似度作为**预留演进方向**记录于此。
