# 教育平台 AI 客服服务压测报告

> 执行时间：2026-09-24（Asia/Shanghai）<br>
> 性质：本地 Docker Compose 单机容量验证，不作为生产 SLA 承诺<br>
> 结论：500 WebSocket、200 msg/s 接入、100 QPS 财务和 20% LLM 超时降级通过；1000 msg/s 突发和单 worker 消费能力未通过。

## 1. 环境与口径

| 项目 | 实测配置 |
| --- | --- |
| 宿主/容器 | macOS arm64 / Docker Linux Ubuntu 24.04.4 aarch64 |
| Docker 资源 | 2 vCPU / 4,094,455,808 bytes（约 3.81 GiB） |
| Docker | Client 29.8.1 / Server 29.5.2 |
| 工具 | Locust 2.32.6 |
| 服务 | FastAPI + PostgreSQL + Redis + NATS JetStream + Qdrant + worker |
| LLM | 本地 Mock LLM，不消耗真实 DeepSeek 额度 |
| 限流 | 临时调高租户/用户业务限流；LLM 全局调度策略保留 |

题目建议环境为 8C16G，本机只有 2C4G。本报告同时展示需求目标和本机实测上限，不用硬件差异掩盖未达标项。

## 2. 目标场景结果

| 场景 | 目标 | 实测 | P50 | P95 | P99 | 失败率 | 结论 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| WebSocket 长连接 | 500 | 500/500，保持 60s | 160ms 建连 | 250ms | 260ms | 0% | **通过** |
| 稳定消息接入 | 200 msg/s×5min | 59,675 条，199.12 msg/s | 10ms | 150ms | 220ms | 0% | **接入通过，消费未通过** |
| 突发消息接入 | 1000 msg/s×30s | 10,784 条，370.90 msg/s | 1.2s | 3.9s | 6.2s | 0% | **未通过** |
| 财务查询 | 100 QPS，P95<500ms | 2,908 次，100.08 QPS | 10ms | 130ms | 160ms | 0% | **通过** |
| 20% LLM 超时降级 | 不断链，可用回复 | 129 ACK / 124 完整回复 | ACK 3ms | ACK 9ms | ACK 100ms | 0% | **通过** |
| LLM 超时下首回复 | P95<1.5s | 124 次 | 1.1s | 1.2s | 1.2s | 0% | **通过** |
| LLM 超时下完整回复 | P95<3s | 124 次 | 1.1s | 1.2s | 1.2s | 0% | **通过** |

`199.12 msg/s` 与 200 msg/s 的偏差为 -0.44%，可视为调度误差；但稳定流结束时入站 consumer 仍有 52,836 pending + 1,000 ack pending，因此只能判定接入层达标，不能宣称端到端容量达标。

## 3. 资源与队列

| 场景 | 容器合计 CPU 峰值 | 容器合计内存峰值 | im-inbound pending 峰值 | ack pending 峰值 |
| --- | ---: | ---: | ---: | ---: |
| 500 WebSocket | 28.30% | 1,036.0 MiB | 0 | 0 |
| 200 msg/s | 185.21% | 1,168.76 MiB | 52,836 | 1,000 |
| 1000 msg/s 突发 | 183.89% | 1,160.28 MiB | 约 7.1 万（含前置稳定流） | 1,000 |
| 100 QPS 财务 | 55.28% | 942.8 MiB | 本场景暂停 worker，不计队列 | — |

2 vCPU 在 200/1000 msg/s 场景中已接近饱和。单 worker 还受“真实 DeepSeek 每秒最多启动 20 次”全局保护策略约束，观察到的积压恢复约为 25 条/秒。这是预期的保护性背压，但不满足 200 msg/s 端到端容量目标。

## 4. 瓶颈与扩容方案

1. **API/PostgreSQL 入口瓶颈**：1000 msg/s 下只有 370.90 msg/s，P95 3.9s。需在 8C16G 专用环境扩容 API，增加 PostgreSQL 连接池并复核写入索引/事务路径。
2. **消费端队头阻塞**：单 worker 不能追平 200 msg/s。需水平扩容 worker，按会话键保证局部有序，同时增加消费并发度。
3. **LLM 调度上限**：20 starts/s 是为避免真实 DeepSeek TCP 连接雪崩的业务约束。应对 RAG/固定话术先行短路和缓存，只将必要请求进入 LLM 队列。
4. **验收复测**：在 8C16G 独占机器上使用多 API/多 worker 重跑三轮，以 P95/P99、最大积压和恢复时间中位数作为生产容量依据。

## 5. 可复现命令

```bash
make loadtest-ws-500
make loadtest-stable-200
make loadtest-burst-1000

LOADTEST_SCENARIO=finance LOADTEST_RATE_PER_USER=5 \
USERS=20 SPAWN_RATE=20 RUN_TIME=30s CSV_PREFIX=finance100 \
make loadtest-recorded
```

20% LLM 超时场景使用 Mock 的 `delay_every=5`、`delay_ms=3000`，worker 超时为 1s，再执行：

```bash
LOADTEST_SCENARIO=llm-timeout USERS=5 SPAWN_RATE=5 \
RUN_TIME=30s CSV_PREFIX=llm-timeout-20 make loadtest-recorded
```

## 6. 原始证据

- `report/raw/ws500_*`：500 WebSocket。
- `report/raw/stable200_*`：200 msg/s 稳定流。
- `report/raw/burst1000_*`：1000 msg/s 目标突发。
- `report/raw/finance100_*`：100 QPS 财务。
- `report/raw/llm-timeout-20_*`：20% LLM 超时降级。
- `report/raw/*-observability.jsonl`：Docker 资源与 NATS consumer 连续采样。
- `report/raw/loadtest-backlog-final.json`：清理前队列状态。

压测后已保存 NATS 积压证据，并清空本轮产生的测试事件流，避免影响后续验收。PostgreSQL 中的租户、知识库与业务数据未删除。
