## 1. 验收结论

**建议结论：可作为面试 Demo 交付，不应宣称已达生产容量。**

- 功能、安全、多租户隔离、自动化测试、RAG 评测、故障恢复和 500 WebSocket 长连接已通过。
- 200 msg/s 稳定接入达到 199.12 msg/s，ACK P95 150ms、零 HTTP 错误；但单 worker 不能追平，形成明显队列积压。
- 1000 msg/s 突发在 2C4G 本机只达到 370.90 msg/s，P95 3.9s，该项未通过。
- 100 QPS 财务查询、20% LLM 超时降级、Redis/NATS/worker 故障恢复均通过。

## 8. 未通过项与优化方案

### P1：1000 msg/s 入口容量

2C4G 单 API 实例只达到 370.90 msg/s，CPU 合计峰值约 183.89%。建议在 8C16G 专用环境扩展 API 实例，调整 PostgreSQL 连接池，重跑三轮。

### P1：消费端追平能力

200 msg/s 停止时有 52,836 pending + 1,000 ack pending。根因是单 worker 串行消费与 DeepSeek 全局 20 starts/s 保护策略的叠加。建议将固定话术/RAG 缓存短路与真实 LLM 调用分层，增加 worker 实例和消费并发，以 conversation_id 做有序键。

### P2：provider 真流式

当前 WebSocket 协议具有 `reply.start/chunk/end`，但 LLM client 先生成完整文本，再在出站层分块。Demo 时延指标可通过，生产应接入 provider `stream=true`。
